## 背景・課題

Phase 2 の中で最もリスクが高い認証基盤の実装。外部レビュー
（`docs/基本設計書_Phase2_レビュー報告書_20260725.md`）で重大・高リスクの指摘が集中していた
領域であり、以下の要求を満たす必要があった。

- `SameSite=Strict` を使わない（OAuthコールバックが壊れるため）＋CSRFトークンによる別途防御
- IDトークンの厳密な検証（JWKS署名、iss/aud/exp/nonce、Microsoft `common` の iss/tid 整合）
- メールアドレスによるアカウント自動統合の禁止
- 無効化・降格が既存セッションへ即時反映されること

## 検討した選択肢

### OIDC実装方式

ADR `20260731_oidc実装方式とライブラリ選定.md` に詳細を記録。要約すると、
IDトークン検証は `firebase/php-jwt` に任せ、フロー本体（Discovery・認可URL・トークン交換）は
cURLで自前実装する方針を採用した。`league/oauth2-client` を使っても「一番難しいIDトークン
検証は結局自分で書く」構図になること、Microsoft `common` の issuer 検証が一般的な
ライブラリのロジックでは正しく扱えないことが主な理由。

### UserInfo エンドポイントの扱い

基本設計書 §3.1 には「UserInfo の sub と ID トークンの sub の一致を確認する」とあり、
UserInfo を必ず呼ぶ前提の書きぶりだった。しかし検証済みのIDトークンに `email` が含まれる
通常のケースでは、UserInfo を呼ぶ必要がない（往復が増えるうえ、トークン差し替えの機会を
自ら作ることになる）。

そこで **IDトークンに email があればUserInfoを呼ばず、無い場合（Microsoftのアカウント種別に
よってはあり得る）のみ呼び、その際に必ず sub の一致を確認する** 方式にした。設計の意図
（トークン差し替え防止）は満たしつつ、攻撃面をより小さくできる。

## 実装の概要

```
server/src/
├── Support/
│   ├── HttpClient.php     # 証明書検証必須・リダイレクト追従なしのcURLラッパー
│   └── Response.php       # JSON応答・no-store・相関IDつきエラー
├── Repository/
│   ├── UserRepository.php
│   ├── AllowListRepository.php
│   └── AuditLogRepository.php
├── Auth/
│   ├── ProviderConfig.php    # Google/Microsoftの設定（MS_TENANT既定はcommon）
│   ├── Discovery.php         # Discovery Document取得（エンドポイントをハードコードしない）
│   ├── AuthTransaction.php   # state/PKCE/nonce。取り出しと同時に破棄＝一回限り
│   ├── OidcClient.php        # 認可URL構築・トークン交換・UserInfo
│   ├── IdTokenVerifier.php   # ★署名・iss・aud/azp・nonce・sub の検証
│   ├── AccessPolicy.php      # 許可ドメイン/アドレス、Googleのhd・email_verified
│   ├── AccountResolver.php   # identity解決（provider+sub主キー、自動統合しない）
│   ├── SessionManager.php    # Cookie属性・CSRF・security_stamp・アイドルタイムアウト
│   └── AuthException.php
└── Http/
    ├── Router.php
    ├── CsrfGuard.php         # X-CSRF-Token + Origin/Referer検証
    └── Controller/AuthController.php
```

`public/api/index.php` はフロントコントローラとして、ローカル（`server/`をマウント）と
本番（公開ディレクトリと`mindmap-app/`が分離）の両方のレイアウトで autoload を解決できる
ようにした。

### セキュリティ上の設計判断（コード上のポイント）

- **署名アルゴリズムを RS256 のみに固定**。`alg=none` やHMAC共通鍵への混同攻撃を防ぐ。
  `JWK::parseKeySet()` が生成する Key は鍵自身がアルゴリズムを保持するため、ヘッダの `alg` を
  信用しない。
- **Microsoft `common` の issuer 検証**: Discovery の issuer は
  `https://login.microsoftonline.com/{tenantid}/v2.0` というプレースホルダ。IDトークンの `tid`
  でこれを組み立て直して比較する。`tid` を issuer 文字列の組み立てに使う以上、GUID形式かを
  先に検証してから使う（パストラバーサル的な細工を防ぐ）。
- **`hd` とメールドメインの一致確認**: `hd` だけを見て許可すると、許可ドメインの `hd` を持つ
  トークンで別ドメインのメールアドレスを名乗る余地が生じるため、両者の一致まで確認する。
- **Google個人アカウントはドメイン許可では入れない**: `hd` を持たないコンシューマアカウントは
  個別のメール許可（FR-08-4）でのみ利用可能とする。`gmail.com` を許可ドメインに入れても
  全Gmailユーザーが入れるわけではない。
- **`security_stamp`**: ロール変更・無効化のたびに再生成し、リクエストごとにDBと突き合わせる。
  これにより再ログインを待たずに既存セッションが失効する（NFR-S-10）。

## 試行錯誤・ハマったこと

### `curl_close()` が PHP 8.5 で非推奨 → ヘッダ送信が壊れる

`GET /api/auth/google/redirect` が 302 ではなく 200 を返す不具合が出た。原因は
`HttpClient` 内の `curl_close()`。PHP 8.0 以降 `curl_init()` は `CurlHandle` オブジェクトを
返し GC で解放されるため `curl_close()` は無効化されており、**8.5 で非推奨になった**。
`display_errors` が有効なローカルでは Deprecated 通知が本文として出力され、その時点で
ヘッダが送信済みになり `http_response_code()` も `header('Location')` も効かなくなっていた。

本番の heteml も PHP 8.5 のため、`display_errors=Off` でも潜在的な問題を抱えることになる。
`curl_close()` の呼び出しを削除（`unset($ch)` のみ）して解決した。
**PHP 8.5 を採用したこと（Step 0で確定）が、古い書き方を持ち込むと表面化する好例だった。**

### テストの固定値が CHAR(32) を超過

`security_stamp` のテスト用リテラルが33文字で `SQLSTATE[22001] Data too long` になった。
`str_repeat('a', 32)` に置き換えて解決。桁数が仕様（CHAR(32)）で決まっている値は、
リテラルを手書きせず生成するほうが安全。

## テスト

PHPUnit 12 を dev 依存として導入し、**34テスト・66アサーションがすべてパス**することを
Docker上で確認した（`docker compose exec php ./vendor/bin/phpunit`）。

- `IdTokenVerifierTest`（11件）: 自前でRSA鍵を生成してJWKSを組み立て、攻撃者の鍵による署名、
  誤ったaud、期限切れ、nonce不一致、iss偽装、azp不一致、Microsoftのiss/tid不整合、tid欠落、
  tid形式不正を**すべて拒否すること**を検証
- `AuthTransactionTest`（7件）: state の不一致・再利用・失敗後の再利用・期限切れ・
  provider違いの拒否、PKCE code_challenge が S256(base64url) であること
- `AccountResolverTest`（11件）: 初回ログイン、再ログイン、**初期管理者(identity 0件)の
  初回ログイン**（v2.3修正の回帰防止）、退職者メール再割当ての自動統合拒否、プロバイダ跨ぎの
  統合拒否、許可判定6ケース
- `SessionManagerTest`（5件）: 無効化ユーザーのセッション失効、security_stampローテーション
  （＝降格）後の失効、アイドルタイムアウト、CSRFトークン検証

実サーバーに対する疎通も確認した。`/api/auth/google/redirect` が Google の**実際の**
Discovery Document を取得し、PKCE(S256)・state・nonce を含む正しい認可URLへ302すること、
CSRF拒否（Origin無し→`invalid_origin`、トークン無し→`invalid_csrf_token`）、405/404、
未ログイン時の `/api/auth/me` → 401 を確認した。
