# ADR: OIDC実装方式とライブラリ選定

**日付**: 2026-07-31
**ステータス**: 承認済み
**関連**: 基本設計書_Phase2.md §3.1, §9、開発ステップ_Phase2.md Step 3、同 §12 未決定事項 No.1

## 背景

Phase 2 では Google と Microsoft の SSO（OAuth 2.0 / OpenID Connect）でログインできる必要がある
（FR-07-1, FR-07-2）。基本設計書_Phase2.md §9 では暫定的に `league/oauth2-client` +
`league/oauth2-google` を候補として挙げつつ、「Microsoft の `common` エンドポイント
（マルチテナント＋個人アカウント）でのIDトークン検証に対応できるかを構築フェーズで実装検証の
うえ確定する」として未決定（§12 未決定事項 No.1）にしていた。

外部レビュー（`docs/基本設計書_Phase2_レビュー報告書_20260725.md` §2.6）では、IDトークン検証の
不備が「高」リスクとして指摘されており、特に以下が要求されている。

- Discovery Document / JWKS を利用した署名検証、許可アルゴリズムの固定、`kid` による鍵選択
- `iss` / `aud` / `exp` / `nonce` の検証
- Microsoft の `common` ではテナントごとに `iss` が異なるため、`iss` と `tid` の整合確認
- PKCE S256、`state` の一回限り使用

## 決定内容

**IDトークンの検証には `firebase/php-jwt`（v7.1）を使用し、OAuth 2.0 / OIDC のフロー本体
（Discovery、認可URL構築、トークン交換、UserInfo取得）は cURL による自前実装とする。**

`league/oauth2-client` およびそのプロバイダ実装は採用しない。

## 理由

1. **危険な部分だけをライブラリに任せる**: 自前実装が最も危険なのは JWT の署名検証である
   （`alg=none` 混同攻撃、公開鍵と共通鍵の取り違え、`kid` によるキー選択、鍵ローテーション
   への追随など）。ここは実績あるライブラリに任せるべきで、`firebase/php-jwt` は
   `Firebase\JWT\JWK::parseKeySet()` と `JWT::decode()` により JWKS ベースの検証を安全に
   行える。`composer audit` でも既知の脆弱性なし。

2. **フロー本体はライブラリの恩恵が小さい**: OIDC の Discovery（1回のGET）、認可URLの構築
   （クエリ文字列の組み立て）、トークン交換（1回のPOST）は仕様が明確で、実装は数十行に収まる。
   `league/oauth2-client` はプロバイダ差異を吸収する抽象化が主目的だが、今回は Google /
   Microsoft ともに標準的な OIDC Discovery に準拠しているため、抽象化の恩恵が小さい。

3. **Microsoft `common` との相性**: `common` エンドポイントでは発行者 `iss` がテナントごとに
   `https://login.microsoftonline.com/{tid}/v2.0` と変化するため、「Discovery Document に
   書かれた固定の issuer と完全一致するか」という一般的なライブラリの検証ロジックでは
   正しく扱えない（Discovery上の issuer は `{tenantid}` というプレースホルダを含む）。
   IDトークンの `tid` クレームを取り出して issuer を組み立て直す、という非標準の検証が
   必要になるため、検証処理を自分の管理下に置けるほうが確実で、レビュー可能性も高い。

4. **依存の最小化**: 基本設計書_Phase2.md §9 の方針（DBアクセスはPDO標準、Zipは標準拡張、
   追加ライブラリを最小限に）と一貫する。heteml 上での Composer 運用は SSH 経由の手動
   インストールであり、依存が少ないほど運用が楽になる。

## 代替案

### 代替案A: `league/oauth2-client` + プロバイダ実装

- メリット: OAuth2 フローの定型部分を書かずに済む。PKCE・state のヘルパーがある
- デメリット: IDトークン検証は結局スコープ外で別途実装が必要（このライブラリはOAuth2用で
  OIDCのIDトークン検証は責務外）。Microsoft 用のサードパーティ製プロバイダはメンテナンス
  状況にばらつきがあり、`common` の issuer 検証を正しく扱えるか個別検証が必要。結果として
  「ライブラリを入れたのに一番難しい部分は自分で書く」構図になる

### 代替案B: `jumbojett/openid-connect-php` 等のフルOIDCクライアント

- メリット: Discovery からIDトークン検証まで一括で面倒を見てくれる
- デメリット: 内部の検証ロジックがブラックボックスになりやすく、外部レビューで要求された
  検証項目（`iss`/`tid` 整合、`azp`、`nonce` の一回限り性など）が実際に行われているかを
  確認・保証しづらい。セキュリティ要件が明示的に列挙されている本プロジェクトでは、
  検証内容を明示的にコードで表現できるほうが望ましい

## 影響・トレードオフ

- **利点**: 検証ロジックが `src/Auth/IdTokenVerifier.php` に集約され、レビュー報告書 §2.6 の
  要求項目と1対1で対応づけて確認できる。テストも書きやすい。
- **欠点**: OAuth2 フローの定型部分（トークン交換のエラーハンドリング等）を自分で保守する
  必要がある。プロバイダ側の仕様変更に自力で追随しなければならない。
- **緩和策**: Discovery Document を毎回参照する実装とし、エンドポイントURLをハードコード
  しない。これによりプロバイダ側のエンドポイント変更には自動的に追随できる。
- **将来**: 対応プロバイダを大幅に増やす場合（3つ以上）は、抽象化のためにライブラリ導入を
  再検討する余地がある。その場合もIDトークン検証は本ADRの方針を維持する。
