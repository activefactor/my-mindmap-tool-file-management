# 開発ログ: Phase 2 リージョン制限・SSO種別・許可ドメインの仕様解釈

**日付**: 2026-07-25
**担当**: Claude Code（要件確認セッション）
**関連機能**: FR-07（認証・SSO）, FR-08-3/08-4（許可ドメイン・許可アドレス管理）, NFR-Region-1

---

## 背景・課題

サーバーレス版（Phase 1）からレンタルサーバー（heteml）版（Phase 2）への移行にあたり、
ユーザーから「使えるリージョンは日本のみに限定したい」「SSOはMS/Gmail対応」「管理者が指定ドメインを
管理できるようにしたい」という要求があったが、実現方式が複数考えられ、要件定義書に書き下す前に
解釈を確定する必要があった。

## 検討した選択肢

### リージョン制限について

- **選択肢 A**: アプリ側で GeoIP 等により日本国外からのアクセスを IP ベースでブロックする
  - メリット: 最も厳格。SSOアカウントの流出時にも国外アクセスを防げる
  - デメリット: heteml で GeoIP DB / モジュールが使えるか不明。実装・運用コストが高い
- **選択肢 B**: heteml が日本国内データセンターであることのみを要件として明記する
  - メリット: 実装コスト低い
  - デメリット: 「利用者を日本に限定したい」という意図（データ所在地ではなくアクセス主体の制限）に応えられない
- **選択肢 C（採用）**: SSO側のテナント・アカウント制限（＝許可ドメイン／許可アドレス制御）で事実上絞る
  - メリット: 追加のIP判定ロジックが不要。既に要求されている「指定ドメインの管理」機能と統合できる
  - デメリット: 許可済みアカウントが海外から利用した場合はブロックできない（IPベースではないため）

### Microsoft SSO の対象アカウント種別

- 職場/学校アカウントのみ（単一テナント）／任意組織の職場学校アカウント（マルチテナント）／
  職場学校＋個人アカウントの3案を提示
- ユーザー回答: **職場/学校アカウント＋個人のMicrosoftアカウントの両方**
  → Azure AD (Entra ID) の `common` エンドポイントを使う前提で設計する

### 許可ドメイン管理の使われ方

- ドメイン単位の一括許可のみ／ドメイン単位＋個別メールアドレスの例外許可の2案を提示
- ユーザー回答: **許可した企業ドメイン＋個別に許可したGmailアドレスの併用**

## 決定した内容とその理由

- リージョン制限は選択肢 C（SSO許可ドメイン／許可アドレスによるアクセス制御）を採用。
  理由: ユーザー自身が「SSO側のテナント・アカウント制限で事実上絞る」を選択しており、
  かつ FR-08-3/08-4（指定ドメイン管理・許可アドレス管理）と実装が一体化するため、
  追加のIPジオブロック機構を持たない方が構成がシンプルになる。
- Microsoft SSO はマルチテナント（`common`）+ 個人アカウント許可で設計する。
- 許可ドメインと許可アドレスは併用可能なリストとして管理コンソールに実装する
  （FR-08-3, FR-08-4 として要件定義書に明記）。

## 実装の概要

今回はコード実装ではなく、上記の解釈を `要件定義書.md` v2.0 の FR-07-3, FR-08-3, FR-08-4,
