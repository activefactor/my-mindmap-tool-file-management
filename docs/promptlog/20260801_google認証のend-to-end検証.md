# プロンプトログ: Google SSO の設定値提示と end-to-end 検証

**日付**: 2026-08-01

## ユーザーの指示（要約）

1. 「googleのアプリケーションの認証設定で、承認済みの JavaScript 生成元 / 承認済みのリダイレクト
   URI 想定している上記の情報をください。それを登録します」
2. 「一旦、Googleだけで進めたい。MSはまた必要に応じて行いたい、IDとシークレットの情報はどこに
   書けばいいんだっけ？」
3. `.env` 更新後、ブラウザでのログインを実施し結果を報告（`/dashboard` へ遷移、
   `/api/auth/me` が JSON を返した）
4. 「規約上はそうだが、運用を始めてから、本番と開発とでブランチを分ける形でいいと思っているので、
   現状はmainに直接コミットでいいよ」

## 主な決定・確認事項

- **Microsoft は当面見送り**（ユーザー判断）。必要になった時点でアプリ登録を行う。
  コード側は実装・単体テスト済みのため、`.env` の値を設定するだけで有効になる。
- **承認済みの JavaScript 生成元は本方式では不要**であることを説明した。今回はサーバーサイド
  完結のフロー（PHP が 302 でプロバイダへ送り、コールバックも PHP が受け、トークン交換も
  クライアントシークレットを用いてサーバー間で行う）のため、ブラウザから Google のオリジンへ
  直接リクエストが飛ばない。登録しても害はないため、将来方式を変える場合に備えて登録可とした。
- 提示したリダイレクトURI: `http://localhost:8080/api/auth/google/callback`（ローカル）と
  `https://mindmap.activefactor.org/api/auth/google/callback`（本番）。同一クライアントに
  両方登録しておけば `.env` の切り替えだけで両環境に対応できる。
- 検証アカウントが個人 Gmail のため、`INITIAL_ALLOWED_DOMAIN` は空とし
  `INITIAL_ADMIN_EMAIL` による個別メール許可で運用することを案内した
  （`hd` クレームを持たない個人アカウントはドメイン許可では通らない設計のため）。
- **ブランチ運用**: 開発標準ルール §4.1 では `main` への直接コミットを禁止しているが、
  運用開始までは `main` へ直接コミットしてよいとのユーザー判断。本番と開発のブランチ分離は
  運用開始時に行う。規約と実態が食い違ったままにならないよう、§4.1 に「Phase 2 構築期間中の
  例外」として明文化し、Step 11 のチェックリストに本則への移行を追加した。

## 対応内容

- `.env` 更新後、`docker compose up -d --force-recreate php` でコンテナを作り直し、
  マイグレーションとシードを実行。
- 実アカウントでの end-to-end ログインを検証し、DB・監査ログ側の記録をすべて確認
  （詳細は `server/docs/devlog/20260731_step3_auth.md` の追記を参照）。
  identity 0件の既存ユーザー（初期管理者）が初回ログインとして紐付くことを実プロバイダ相手で
  確認できた点が最大の成果。
- ドキュメント更新:
  - `docs/開発ステップ_Phase2.md` v1.5→v1.6（Step 3 を完了に変更、検証結果と登録した
    OAuth クライアント設定値を記録、Step 1 の残項目を消化、Microsoft 見送りを明記）
  - `server/docs/devlog/20260731_step3_auth.md`（検証結果を追記）
  - `server/README.md`（Step 3 時点の内容に更新。DB初期化・SSO設定手順・テスト実行、
    および `.env` 変更時はコンテナ再生成が必要な点を追記）
  - `docs/開発標準ルール.md` v1.2→v1.3（§4.1 に構築期間中のブランチ運用の例外を追記）
  - `CLAUDE.md`（Phase 状況の更新、ブランチ運用の例外を反映）
