## 0. 全ステップ共通のルール

- ブランチは `feature/phase2-<ステップ名>` の形式で作成する（例: `feature/phase2-auth`）。
- 各ステップ完了時、`mindmap-tool/docs/devlog/` に開発ログを記録する（技術的な判断があった場合は
  `mindmap-tool/docs/adr/` にも記録する）。
- 各ステップのチェックリストが全て埋まってから次のステップへ進む。埋まらない項目がある場合は
  未決定事項として本書または基本設計書_Phase2.md §12 に追記し、ユーザーに確認する。
- 本書のチェックリストは `docs/セキュリティポリシー.md` §7「Phase 2 追加チェックリスト」を
  補完するものであり、矛盾する場合はより具体的な本書の記載を優先し、セキュリティポリシー側も
  同じ内容に更新する。

## Step 3: 認証基盤（OAuth・IDトークン検証・セッション・許可判定）

**依存**: Step 2
**対応**: FR-07, NFR-S-5/6/9/10、基本設計書_Phase2.md §3.1, §6.1

このステップは Phase 2 の中で最もリスクが高い部分（外部レビューで重大指摘が集中した領域）
のため、他のステップより手厚くチェックリストを設ける。

### ライブラリ選定（ADR化必須）

- [ ] Google/Microsoft 双方の OAuth・OIDC 実装方式を検証し、ライブラリ（`league/oauth2-client`
      系か、IDトークン検証込みで自前実装するか）を確定する（基本設計書_Phase2.md §12 未決定
      事項 No.1）。選定理由を ADR に記録する

### 実装項目

- [ ] `state`（乱数・一回限り・有効期限10分・provider紐付け）、PKCE（`code_verifier`/
      `code_challenge` S256）、`nonce` の生成・セッション保存・検証を実装する
- [ ] Discovery Document・JWKS を用いたIDトークンの署名検証を実装する（`alg=none`拒否、
      `kid`によるキー選択）
- [ ] `iss`/`aud`/`exp`/`nonce` の検証を実装する。Microsoftは`iss`のテナント部分と`tid`
      クレームの整合を確認する
- [ ] UserInfoの`sub`とIDトークンの`sub`が一致することを確認する
- [ ] 許可判定ロジック（許可ドメイン／許可アドレス、大文字小文字を無視した比較）を実装する
- [ ] Googleログインで`hd`クレームによる追加チェックを実装する（該当する場合）
- [ ] identity解決ロジック（`provider`+`provider_user_id`で検索 → 無ければメール確認 →
      新規ユーザーの場合のみ作成、既存メールと衝突する場合は`login_denied_conflict`で拒否）
      を実装する
- [ ] セッションCookieを`HttpOnly`/`Secure`/`Path=/`/`SameSite=Lax`で発行する
- [ ] CSRFトークンの発行・`X-CSRF-Token`ヘッダー検証ミドルウェアを実装する
- [ ] `security_stamp`・`status`をリクエストごとに確認するミドルウェアを実装する
- [ ] ログイン成功・拒否（許可リスト外／衝突／無効化済み）をそれぞれ監査ログに記録する
      （トークン類は記録しない）
- [ ] ログアウトAPI（CSRF検証込み）を実装する
- [ ] アイドルタイムアウト（既定60分）を実装する

### テスト（基本設計書_Phase2_レビュー報告書_20260725.md §7「認証」を参照）

- [ ] `state`の不一致・期限切れ・再利用を拒否するテスト
- [ ] 不正署名・誤った`aud`・期限切れIDトークンを拒否するテスト
- [ ] Microsoftの`iss`と`tid`が不一致のトークンを拒否するテスト
- [ ] 同一メールで異なる`sub`（＝異なる主体）を自動統合しないテスト
- [ ] 無効化されたユーザーの既存セッションが次のリクエストで使えなくなるテスト

**完了条件**: 上記すべての実装・テストが完了し、Google/Microsoft 双方でログイン
（開発者コンソール登録済みのテストアカウント）が成功することを確認済みであること。

## Step 9: フロントエンドの保存／オープン状態管理統合

**依存**: Step 5, Step 7
**対応**: FR-12, FR-13、基本設計書_Phase2.md §3.6, §3.7

      の状態を分離して実装する
- [ ] `useServerAutosave` フックで、保存リクエストの直列化（1件のみin-flight）・
      デバウンス・`revision`送信を実装する
- [ ] サーバーからの409応答時に、ユーザーへ再読み込みを促す通知を表示する
- [ ] 「一覧に戻る」操作時に、保留中の変更をflushし、保存完了（または失敗）を待ってから
      遷移することを実装する
- [ ] 「開く」でローカルファイルを読み込んだ場合、必ず`binding = local`（新規セッション）に
      切り替わり、既存の`mindmapId`が破棄されることを確認する
- [ ] `autosaveTarget`のみを`local`に切り替えた場合は`mindmapId`が維持されることを確認する
- [ ] サーバー保存失敗時、IndexedDBに`${user_id}_${mindmap_id}`をキーとしてフォールバック
      保存することを実装する

### テスト

- [ ] 最後の編集直後に「一覧に戻る」を押しても内容が保存されることを確認するテスト
- [ ] ローカルファイルを開いてもサーバー上のマップが上書きされないことを確認するテスト
- [ ] 別ユーザーでログインした際に前ユーザーのローカルフォールバックが表示されないことを
      確認するテスト

**完了条件**: オートセーブ・保存先切替・開く動作がレビュー指摘（データ消失・誤上書き）を
再現しないことを確認済みであること。
