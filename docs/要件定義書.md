**バージョン**: 2.1  
**作成日**: 2026-04-11  
**更新日**: 2026-07-25  
**ステータス**: 承認済み（Phase 2）

> Phase 1（本書 v1.4 まで）はサーバーレス版として承認・リリース済み。

## 1. プロジェクト概要

### 1.1 背景・目的

社内での情報共有手段として、視覚的に構造化されたマインドマップツールを内製する。
既存の外部SaaSに依存せず、将来的なAI連携を見据えた独自ツールとして開発する。

Phase 1 ではサーバーを持たない静的Webアプリとして構築したが、Phase 2 ではレンタルサーバー
（heteml）上に認証・保存基盤を構築し、複数ユーザーがそれぞれのマインドマップをサーバー上に
保存・整理できる状態へ移行する。

### 1.2 対象ユーザー

| ユーザー種別 | 概要 |
|-------------|------|
| 社内スタッフ全般 | 情報整理・ブレインストーミングに使用 |
| プロジェクトマネージャー | 計画・議事録の可視化に使用 |
| システム管理者（Phase 2） | ユーザーのロール管理・許可ドメイン管理・システム管理を行う |
| （将来）AI利用者 | AI連携機能を通じた情報整理・要約 |

### 1.3 スコープ

**対象**: Webブラウザで動作するマインドマップツール（Phase 2 以降はサーバー側の認証・保存基盤を含む）  
**対象外**: モバイルアプリ、デスクトップアプリ、外部サービス連携、リアルタイム共同編集（将来 Phase 4 で検討）

### 3.3 Phase 2 機能要件

Phase 2 では、Phase 1 のマインドマップ編集機能（FR-01〜FR-06）はそのまま維持したうえで、
レンタルサーバー（heteml、PHP + MySQL、SSH/Composer 利用可）上に認証・保存基盤を追加する。

#### FR-07 認証・SSO ログイン

| ID | 要件 | 詳細 |
|----|------|------|
| FR-07-1 | Google SSO ログイン | OAuth 2.0 / OIDC で Google アカウントによるログインができる |
| FR-07-2 | Microsoft SSO ログイン | OAuth 2.0 / OIDC で Microsoft アカウントによるログインができる。職場/学校アカウント・個人アカウントの両方に対応する（マルチテナント＝ `common` エンドポイントを使用） |
| FR-07-3 | 許可ドメイン／許可アドレスによるアクセス制御 | SSO 認証後、認証済みメールアドレスの **ドメインが許可ドメインリストに含まれる場合**、または **メールアドレス自体が許可アドレスリストに含まれる場合**のみログインを許可する。いずれにも該当しない場合はログインを拒否し、その旨をメッセージ表示する |
| FR-07-4 | セッション管理 | ログイン状態をサーバーセッションで管理する。一定時間操作がない場合は自動的にログアウトする |
| FR-07-5 | ログイン後遷移 | ログイン成功後はダッシュボード画面へ遷移する |
| FR-07-6 | ログアウト | ユーザーは任意のタイミングでログアウトできる |

> **リージョン制限の実現方法**: 地理的 IP ブロックは行わない。FR-07-3 の許可ドメイン／許可アドレス
> 制御により、日本国内の許可された組織・利用者のみがログインできる状態を実質的に担保する。

#### FR-08 管理コンソール（管理者ロールのみアクセス可）

| ID | 要件 | 詳細 |
|----|------|------|
| FR-08-1 | ユーザー一覧表示 | 管理者は登録済みユーザー（氏名/メールアドレス/ロール/最終ログイン日時等）の一覧を閲覧できる |
| FR-08-2 | ロール管理 | 管理者は各ユーザーのロール（一般ユーザー／管理者）を変更できる |
| FR-08-3 | 許可ドメイン管理 | 管理者はログインを許可する企業ドメイン（例: `company.co.jp`）を追加・削除できる |
| FR-08-4 | 許可アドレス管理 | 管理者は個別に許可するメールアドレス（社外の Gmail アドレス等）を追加・削除できる |
| FR-08-5 | ユーザー無効化 | 管理者はユーザーを無効化（アクセス停止）し、再有効化できる |
| FR-08-6 | 監査ログ閲覧 | 管理者はログイン履歴・主要操作（削除・ロール変更等）の監査ログを閲覧できる |
| FR-08-7 | ストレージ使用状況閲覧 | 管理者はユーザーごと／全体のマップ件数・保存容量を閲覧できる |

> FR-08-5〜FR-08-7 は一般的な管理機能として本書作成時点で提案した項目。採用可否・優先度は
> 基本設計フェーズで確定する（Section 11 未決定事項も参照）。

#### FR-09 ダッシュボード

| ID | 要件 | 詳細 |
|----|------|------|
| FR-09-1 | マップ一覧表示 | ログイン後遷移したダッシュボードで、自分が保存したマインドマップの一覧（ファイル名・更新日時・所属フォルダ）を表示する |
| FR-09-2 | マップを開く | 一覧からマップを選択すると、そのマップを読み込んだ状態でマインドマップ編集画面が開く |
| FR-09-3 | 一覧に戻る | マインドマップ編集画面から、ダッシュボード（一覧）に戻る導線を提供する |

#### FR-10 フォルダ管理

| ID | 要件 | 詳細 |
|----|------|------|
| FR-10-1 | フォルダ作成 | ダッシュボード上でフォルダを作成できる |
| FR-10-2 | フォルダへのドラッグ＆ドロップ移動 | 一覧上のマップファイルをドラッグし、フォルダにドロップすることでそのフォルダに移動できる |
| FR-10-3 | フォルダ名変更・削除 | 作成したフォルダの名称変更・削除ができる |
| FR-10-4 | フォルダ階層 | Phase 2 ではフォルダは 1 階層のみとする（フォルダ内フォルダは作成不可） |

#### FR-11 ダウンロード

| ID | 要件 | 詳細 |
|----|------|------|
| FR-11-1 | ファイルダウンロード | 一覧上の個々のマップファイルは JSON 形式でダウンロードできる |
| FR-11-2 | フォルダの Zip ダウンロード | フォルダを選択すると、フォルダ内のマップをまとめて Zip 形式に圧縮してダウンロードできる |
| FR-11-3 | Zip の自動削除 | サーバー上に生成した Zip ファイルは、ダウンロード完了後にサーバー上から自動的に削除する（削除タイミングの具体方式は基本設計で確定。ダウンロード配信直後の削除に加え、削除漏れ対策として一定時間後の cron クリーンアップを併用する想定） |

#### FR-12 保存方式（オートセーブへの変更）

| ID | 要件 | 詳細 |
|----|------|------|
| FR-12-1 | オートセーブ | マインドマップ編集画面では、ノード操作のたびにオートセーブが動作する（Phase 1 の localStorage 自動保存の考え方をサーバー保存にも拡張） |
| FR-12-2 | 保存先の選択 | オートセーブの保存先として「サーバー」「ローカル環境（ブラウザ内）」をユーザーが選択できる |
| FR-12-3 | 既存の手動保存機能の維持 | Phase 1 の JSON／テキスト手動保存（ファイルダウンロード）機能はそのまま維持する |

#### FR-13 「開く」動作（サーバー／ローカルでの挙動の違い）

| ID | 要件 | 詳細 |
|----|------|------|
| FR-13-1 | サーバー上のマップを開く | サーバーに保存されたマップは、ダッシュボードの一覧から選択して開く（FR-09-2 と同じ導線） |
| FR-13-2 | ローカルファイルを開く | ローカルの JSON／テキストファイルを開く操作は、現在編集中のサーバー保存マップを **上書きせず**、新規（未保存）マップとして開く |

#### FR-14 マップ削除・ゴミ箱・復元

サーバー保存されたマップの削除は誤操作による完全なデータ消失を避けるため、即時の物理削除ではなく
ソフトデリート（ゴミ箱）とする。

| ID | 要件 | 詳細 |
|----|------|------|
| FR-14-1 | マップ削除（ソフトデリート） | ダッシュボードの一覧からマップを削除すると、物理削除はせず「削除済み」状態にする。削除前に対象マップ名を明示した確認ダイアログを表示する |
| FR-14-2 | ゴミ箱一覧表示 | ユーザーは削除済みマップの一覧（ゴミ箱）を閲覧できる |
| FR-14-3 | 復元 | ゴミ箱内のマップを選択し、元の状態（フォルダ所属を含む）に復元できる |
| FR-14-4 | 完全削除 | ユーザーはゴミ箱内のマップを完全に削除（物理削除）できる。完全削除前に確認ダイアログを表示する |
| FR-14-5 | 保持期間による自動完全削除 | ゴミ箱内のマップは、削除操作から一定期間（既定 30 日、`.env` で設定可能）経過後、自動的に完全削除される |

> フォルダ自体の削除（FR-10-3）は、内包するマップをルート直下へ移動させたうえでフォルダのみを
> 削除する（マップはゴミ箱に入らず存続する）。フォルダ自体にはゴミ箱・復元機能を設けない。

---

### 3.4 Phase 3 機能要件（概要）

#### AI ノード自動整理

- 現在のマインドマップ（JSON）をAIに渡し、親子関係・分類を自動再構成する
- 結果はプレビュー表示し、ユーザーが適用を選択できる

#### AI サマリー生成

- マップ全体の構造をAIに渡し、何について書かれているかを日本語で要約する
- 結果はサイドパネルに表示する

---

### 3.5 Phase 4 機能要件（概要・将来）

- 複数ユーザーによる同一マップの共同編集（リアルタイム反映）
- 編集競合の解決（Operational Transform / CRDT 等の検討）
- 共有・権限設定（閲覧のみ／編集可 等）

> Phase 2 の時点では対象外。データ構造（保存先スキーマ等）は将来の共同編集を阻害しない形で設計する。

## 4. 非機能要件

### 4.1 パフォーマンス

| ID | 要件 |
|----|------|
| NFR-P-1 | 500ノードまで快適に動作すること（60fps描画） |
| NFR-P-2 | ノード操作のUI反応が50ms以内であること |
| NFR-P-3 | 初回ロードのバンドルサイズが2MB以内であること |
| NFR-P-4 | ドラッグ中のレイアウト計算がスムーズに動作すること |
| NFR-P-5 | オートセーブのサーバー保存リクエストは非同期・デバウンス処理とし、編集操作の応答性を妨げないこと（Phase 2） |

### 4.2 可用性・耐障害性

| ID | 要件 |
|----|------|
| NFR-A-1 | インターネット接続なしで動作すること（Phase 1。Phase 2 のサーバー保存機能利用時を除く） |
| NFR-A-2 | localStorageのクリア以外でデータが消えないこと（ローカル保存選択時） |
| NFR-A-3 | ブラウザクラッシュ後も直前の状態を復元できること |
| NFR-A-4 | サーバー保存に失敗した場合、ユーザーにエラーを通知し、直近の編集内容をローカルにも保持すること（Phase 2） |
| NFR-A-5 | Zip ダウンロード用の一時ファイルは、正常系・異常系（ダウンロード中断等）を問わずサーバー上に残留し続けないこと（Phase 2） |
| NFR-A-6 | ソフトデリートしたマップ（FR-14）は保持期間内であれば復元できること。保持期間経過後は自動的に完全削除されること（Phase 2） |

### 4.3 互換性

| ID | 要件 |
|----|------|
| NFR-C-1 | Chrome / Edge / Firefox / Safari の最新バージョンで動作すること |
| NFR-C-2 | 画面解像度 1280×768 以上で正常表示されること |

### 4.4 保守性

| ID | 要件 |
|----|------|
| NFR-M-1 | DESIGN.md に定義されたデザイントークンを使用すること |
| NFR-M-2 | DESIGN.md の変更のみでビジュアルの改修が完結できること |
| NFR-M-3 | 開発標準ルールに従ったコーディングであること |
| NFR-M-4 | 意思決定・変更過程を開発ログとして記録すること |

### 4.5 セキュリティ

| ID | 要件 |
|----|------|
| NFR-S-1 | XSS対策として、ノードテキストはエスケープ処理して描画すること |
| NFR-S-2 | ファイルインポート時に不正データのバリデーションを行うこと |
| NFR-S-3 | Phase 2 以降の認証・通信はHTTPS必須とすること |
| NFR-S-4 | セキュリティポリシー（セキュリティポリシー.md）に従うこと |
| NFR-S-5 | SSO のクライアントシークレット・DB接続情報等の機密情報は `.env` で管理し、Git にコミットしないこと（Phase 2） |
| NFR-S-6 | セッション Cookie は `HttpOnly` / `Secure` / `SameSite` を設定すること（Phase 2） |
| NFR-S-7 | ユーザーは自分が所有するマップ・フォルダのみアクセス可能とし、他ユーザーのデータへの認可なきアクセスを防止すること（Phase 2） |
| NFR-S-8 | 管理コンソール（FR-08）は管理者ロールのユーザーのみアクセス可能とすること（Phase 2） |
| NFR-S-9 | 状態を変更するAPI（POST/PUT/DELETE）はCSRFトークン検証を必須とすること。セッションCookieの属性のみに依拠しないこと（Phase 2） |
| NFR-S-10 | ユーザーの無効化・ロール変更・許可ドメイン／許可アドレスの削除は、対象ユーザーの既存セッションに即時反映されること（再ログインを待たない）（Phase 2） |

### 4.6 ホスティング・リージョン（Phase 2）

| ID | 要件 |

## 5. 制約条件

| 項目 | 制約 |
|------|------|
| サーバー | Phase 1 はサーバーを持たない。Phase 2 はレンタルサーバー（heteml）上、PHP + MySQL で稼働する |
| 認証 | Phase 1 は認証なし。Phase 2 は SSO（Google / Microsoft）＋許可ドメイン・許可アドレス制御 |
| 言語 | 日本語UIのみ（Phase 1・2） |
| 外部連携 | SSO プロバイダ（Google / Microsoft）以外の外部連携なし（Phase 1・2） |
| リアルタイムコラボ | Phase 4 以降で検討 |
| フォルダ階層 | Phase 2 では 1 階層のみ（ネスト不可） |
| 機密情報管理 | `.env` で管理し Git にコミットしない。サンプルとして `.env.example` をリポジトリに含める |

## 6. 用語定義

| 用語 | 定義 |
|------|------|
| ノード | マインドマップ上の1つの項目（テキストボックス） |
| ルートノード | マップの最上位ノード（親を持たないノード） |
| 親ノード | 別のノードの直接の上位ノード |
| 子ノード | 別のノードの直接の下位ノード |
| 階層 | ルートから数えた深さ（ルート=0） |
| インデントテキスト | 階層をスペース4つのインデントで表現したテキスト形式 |
| Undo | 直前の操作を取り消す機能 |
| Redo | Undoで取り消した操作を再実行する機能 |
| ドラッグ親子変更 | ノードをドラッグして別のノードにドロップすることで、そのノードの子にする操作 |
| ドロップターゲット | ドラッグ中にドロップ先の候補として強調表示されるノード |
| スナップバック | 空白にドロップした際、自動レイアウト位置に戻る動作 |
| 相対位置レイアウト | ノードのテキスト長によってノード幅が変わっても、親子ノードが重ならないよう間隔を自動調整するレイアウト |
| SSO（シングルサインオン） | Google / Microsoft の既存アカウントを用いてログインできる認証方式 |
| 許可ドメイン | 管理者が登録した、ログインを許可するメールドメイン（例: `company.co.jp`）。ドメイン単位で一括許可する |
| 許可アドレス | 管理者が個別に登録した、ログインを許可する特定のメールアドレス（許可ドメインに属さない例外アカウント向け） |
| ダッシュボード | ログイン後に表示される、マインドマップ一覧・フォルダ管理を行う画面 |
| オートセーブ | ノード操作のたびに自動で保存する仕組み。Phase 2 では保存先をサーバー／ローカルから選択できる |
| ソフトデリート | データを物理削除せず「削除済み」状態にする削除方式。ゴミ箱から復元、または保持期間経過後に完全削除される |
| ゴミ箱 | ソフトデリートされたマップの一覧・復元・完全削除を行う画面 |
