# 開発標準ルール

**バージョン**: 1.3  
**作成日**: 2026-04-11  
**更新日**: 2026-08-01  
**適用プロジェクト**: マインドマップツール（全フェーズ）

---

## 1. 概要

このドキュメントはプロジェクトにおける開発作業の標準ルールを定めます。
コードの品質・一貫性・追跡可能性を保ち、将来の改修・引き継ぎを容易にすることを目的とします。

---

## 2. ディレクトリ・ファイル構成ルール

### 2.1 リポジトリ全体の構成と devlog/ADR/promptlog の置き場所

Phase 2（レンタルサーバー移行）以降、リポジトリは複数コンポーネント
（`mindmap-tool/` フロントエンド、`server/` バックエンド）から成るため、devlog・ADR・
プロンプトログは以下の基準で置き場所を分ける。

```
my-mindmap-tool-file-management/
├── docs/                        # プロジェクト全体のドキュメント（要件定義書・基本設計書等）
│   ├── devlog/                  # コードに紐付かない、計画レベルの開発ログ
│   └── promptlog/               # プロンプトログ（常にここ一箇所）
├── mindmap-tool/                # フロントエンド
│   └── docs/
│       ├── adr/                 # mindmap-tool のコードに関する意思決定記録
│       └── devlog/              # mindmap-tool のコード変更に関する開発ログ
└── server/                      # バックエンド（Phase 2 で追加）
    └── docs/
        ├── adr/                 # server のコードに関する意思決定記録
        └── devlog/              # server のコード変更に関する開発ログ
```

- **判断基準**: そのセッションでコードを変更したかどうかで振り分ける。要件定義・基本設計・
  レビュー対応・git運用などコードを伴わない作業は `docs/devlog/`（ルート直下）。
  `mindmap-tool/` または `server/` のコードを実際に変更した場合は、そのコンポーネントの
  `docs/devlog/` に置く。
- **プロンプトログ**は対象コードの場所によらず常に `docs/promptlog/`（ルート直下）一箇所に
  まとめる。

### 2.2 mindmap-tool 内部のディレクトリ構成

```
mindmap-tool/
├── index.html
├── package.json
├── vite.config.ts
├── tsconfig.json
├── tailwind.config.ts
│
├── docs/                        # ドキュメント類（2.1 参照。mindmap-tool 固有の adr/devlog）
│   ├── adr/                     # 意思決定記録（ADR）
│   │   └── YYYYMMDD_タイトル.md
│   └── devlog/                  # 開発ログ
│       └── YYYYMMDD_内容.md
│
├── public/
│   └── favicon.ico
│
└── src/
    ├── main.tsx                 # エントリーポイント
    ├── App.tsx                  # ルートコンポーネント
    ├── styles/
    │   ├── tokens.css           # DESIGN.md のCSSカスタムプロパティ定義
    │   └── global.css           # グローバルスタイル
    ├── components/              # UIコンポーネント
    ├── hooks/                   # カスタムフック
    ├── utils/                   # ユーティリティ関数
    └── types/                   # 型定義
```

### ファイル命名規則

| 種別 | 命名規則 | 例 |
|------|---------|-----|
| コンポーネント | PascalCase | `MindMapNode.tsx` |
| カスタムフック | camelCase（use プレフィックス） | `useMindMap.ts` |
| ユーティリティ | camelCase | `exportJSON.ts` |
| 型定義ファイル | camelCase | `mindmap.ts` |
| テストファイル | 対象と同名 + `.test` | `exportJSON.test.ts` |
| ADR | `YYYYMMDD_タイトル.md` | `20260411_ライブラリ選定.md` |
| 開発ログ | `YYYYMMDD_内容.md` | `20260411_undo_redo実装.md` |

## 3. コーディング規約

### 3.1 言語・バージョン

- 言語: TypeScript（strict モード必須）
- React: 関数コンポーネント + Hooks のみ使用（クラスコンポーネント禁止）
- `any` 型の使用は原則禁止（やむを得ない場合は `// TODO: 型定義` コメントを付ける）

### 3.2 コンポーネント設計

- 1コンポーネント1ファイルを基本とする
- Props の型定義は同ファイルの先頭で `interface` として定義する
- ビジネスロジックはカスタムフックに分離し、コンポーネントはUIのみを担当する

```typescript
// Good: Props型定義 + ロジック分離
interface MindMapNodeProps {
  node: MindMapNode;
  isSelected: boolean;
  onSelect: (id: string) => void;
}

export const MindMapNode: React.FC<MindMapNodeProps> = ({ node, isSelected, onSelect }) => {
  // UIのみ
};
```

### 3.3 スタイル規約

- スタイル値は **必ず DESIGN.md で定義した CSS カスタムプロパティを使用する**
- コンポーネント内にカラーコード・px 値・font-size 値をハードコードしない

```typescript
// Bad
<div style={{ backgroundColor: '#3B82F6', padding: '8px' }}>

// Good
<div style={{ backgroundColor: 'var(--color-bg-node-root)', padding: 'var(--spacing-2)' }}>
```

### 3.4 状態管理

- ローカル状態: `useState`
- 複雑なノード操作ロジック: `useReducer` + カスタムフック
- グローバル状態: Context API（Phase 1 では外部状態管理ライブラリ不使用）

### 3.5 エラーハンドリング

- ファイルインポート時は必ずバリデーションを行い、不正データは `throw` で拒否する
- ユーザーに影響するエラーはトースト通知で表示する
- コンソールへの `console.error` 出力はエラー種別とコンテキストを明記する

```typescript
// Good
console.error('[importJSON] バリデーションエラー:', error, { input: rawData });
```

## 4. Git 運用ルール

### 4.1 ブランチ戦略

```
main          ← リリース済みコード（直接コミット禁止）
develop       ← 開発統合ブランチ
feature/*     ← 機能開発（例: feature/undo-redo）
fix/*         ← バグ修正（例: fix/node-delete-crash）
docs/*        ← ドキュメントのみの変更
```

#### Phase 2 構築期間中の例外（2026-08-01 決定）

**Phase 2 の構築が完了して運用を開始するまでの間は、`main` への直接コミットを許容する。**

理由: 現状は単独開発かつ本番環境がまだ存在せず、`main` は「リリース済みコード」ではなく
開発の最新状態を指している。この状況で `develop` / `feature/*` を経由しても、レビューも
並行開発も発生しないため保護の実体がない。

運用開始（Phase 2 の本番デプロイ = Step 11）以降は、本番稼働中のコードと開発中のコードを
分離する必要が生じるため、上記のブランチ戦略に移行する。移行は Step 11 の作業項目として扱う。

### 4.2 コミットメッセージ規約（Conventional Commits）

```
<type>(<scope>): <日本語の説明>

[本文: 変更の理由・詳細（任意）]

[フッター: Breaking Change, Issue 番号等（任意）]
```

**type 一覧**

| type | 用途 |
|------|------|
| `feat` | 新機能追加 |
| `fix` | バグ修正 |
| `refactor` | 動作変更を伴わないリファクタリング |
| `style` | スタイル変更（DESIGN.md 反映含む） |
| `docs` | ドキュメント変更のみ |
| `test` | テスト追加・修正 |
| `chore` | ビルド設定・依存関係の更新等 |

**コミット例**

```
feat(node): Tab キーで子ノードを追加する機能を実装

ノードが選択中に Tab を押すと子ノードが追加され、
即座に編集モードに入るようにした。
```

### 4.3 プルリクエスト（PR）ルール

- 1 PR = 1 機能 or 1 バグ修正
- PR 説明に「変更内容」「テスト方法」「スクリーンショット（UI変更時）」を記載する
- セルフレビューを実施してから PR を出す

## 5. 改修時のドキュメント更新ルール

### 5.1 目的

コードとドキュメントの乖離を防ぎ、常に設計書・仕様書が最新の実装を反映した状態を保つ。

### 5.2 更新が必要なタイミング

以下のいずれかに該当する変更を行った場合、**コードの変更と同じコミット（または同じ PR）で**ドキュメントを更新すること。

| 変更の種類 | 例 |
|-----------|-----|
| 新機能の追加 | 新しいショートカットキー、エクスポート形式の追加 |
| 既存機能の仕様変更 | UIレイアウトの変更、動作の変更 |
| 技術スタックの変更 | ライブラリのバージョンアップ、差し替え |
| データ構造の変更 | 型定義の追加・変更 |
| 画面構成・コンポーネント構成の変更 | ファイル追加、ツールバー項目の変更 |

### 5.3 更新対象ドキュメント

| ドキュメント | 更新条件 |
|------------|---------|
| **要件定義書.md** | 機能要件（FR）または非機能要件（NFR）に変化があった場合 |
| **基本設計書_PhaseX.md** | 該当フェーズの設計（画面・コンポーネント・データ・技術スタック等）に変化があった場合 |
| **docs/devlog/YYYYMMDD_タイトル.md** | 機能追加・仕様変更・バグ修正・技術的判断を行った場合（Section 6 参照） |

### 5.4 ドキュメント更新の具体的な作業

1. **要件定義書**: 変更された機能要件の追加・修正、変更履歴テーブルへの記録
2. **基本設計書**: 変更箇所（画面設計・コンポーネント構成・レイアウト定数・技術スタック等）の更新、バージョン・更新日の記録
3. **devlog**: 変更内容・判断の根拠・試行錯誤の記録（Section 6 のフォーマットに従う）

### 5.5 チェックリスト

コードをコミットする前に以下を確認する。

- [ ] 要件定義書の更新が必要か確認した
- [ ] 基本設計書の更新が必要か確認した
- [ ] devlog を作成した
- [ ] 各ドキュメントのバージョン・更新日を更新した

## 6. 開発ログ（devlog）記録ルール

### 6.1 目的

実装時に検討したこと・試行錯誤・判断の根拠を記録し、  
将来の改修や引き継ぎ時に「なぜそうなっているか」を追跡できるようにする。

### 6.2 記録するタイミング

- 新しい機能を実装したとき
- 技術的な選択肢を検討して何かを選んだとき
- バグの原因調査と修正を行ったとき
- 仕様の解釈について判断を下したとき

### 6.3 保存場所

`docs/devlog/YYYYMMDD_タイトル.md`（2.1 の基準に従い、コードを伴う作業なら
`mindmap-tool/docs/devlog/` または `server/docs/devlog/`、コードを伴わない計画レベルの
作業なら リポジトリルート直下の `docs/devlog/`）

### 6.4 ログフォーマット

```markdown
# 開発ログ: [タイトル]

**日付**: YYYY-MM-DD  
**担当**: [名前またはハンドル]  
**関連機能**: [機能名・PR番号等]

---

## 背景・課題

[なぜこの作業が必要になったか]

## 検討した選択肢

### 選択肢 A: [名称]
- 概要: ...
- メリット: ...
- デメリット: ...

### 選択肢 B: [名称]
- 概要: ...
- メリット: ...
- デメリット: ...

## 決定した内容とその理由

[何を選んだか、なぜか]

## 実装の概要

[どのように実装したか（コードの構造・方針）]

## 試行錯誤・ハマったこと

[問題になったこと、試みて失敗したこと、解決方法]

## 今後の課題・TODO

[完了しなかったこと、将来改善すべきこと]
```

### 6.5 開発ログ記録の例

```
docs/devlog/
├── 20260411_ライブラリ選定.md
├── 20260415_undo_redo実装.md
└── 20260420_インデントテキストパース.md
```

## 7. ADR（アーキテクチャ決定記録）

### 7.1 ADR とは

長期的な影響を持つ技術的意思決定を記録するドキュメント。  
devlog が作業ログなのに対し、ADR はアーキテクチャレベルの「なぜそうなっているか」を残す。

### 7.2 保存場所

`docs/adr/YYYYMMDD_タイトル.md`（2.1 の基準に従い、`mindmap-tool/docs/adr/` または
`server/docs/adr/` に置く。ADR は常にコードを伴う技術選定を対象とするため、リポジトリ
ルート直下には置かない）

### 7.3 ADR フォーマット

```markdown
# ADR: [タイトル]

**日付**: YYYY-MM-DD  
**ステータス**: 提案中 / 承認済み / 廃止済み

## 背景

[この決定が必要になった状況]

## 決定内容

[何を採用するか]

## 理由

[なぜこの選択をしたか]

## 代替案

[検討したが採用しなかった選択肢]

## 影響・トレードオフ

[この決定によって生じる制約やトレードオフ]
```

## 8. プロンプトログ

### 8.1 目的

ユーザーからの主要な指示・要求・確認事項を記録し、後日「なぜこの仕様になったか」
「いつ何を依頼されたか」を追跡できるようにする。devlog が実装判断の記録であるのに対し、
プロンプトログはユーザーとのやり取りそのものの記録である。

### 8.2 記録するタイミング

- ユーザーから新しい要求・指示を受けたとき
- 確認質問を行い、ユーザーから回答を得たとき（決定事項として）
- git のコミット・push など、リポジトリの状態を変える操作を行ったとき

### 8.3 保存場所

`docs/promptlog/YYYYMMDD_内容.md`（リポジトリルート直下。2.1 の基準どおり、対象コードの
場所によらず常にここ一箇所にまとめる）

### 8.4 フォーマット

```markdown
# プロンプトログ: [タイトル]

**日付**: YYYY-MM-DD

## ユーザーの指示（要約）

[何を依頼されたか]

## 主な決定・確認事項

[Claude から確認した質問とユーザーの回答、決定事項]

## 対応内容

[更新したファイル・作成した成果物]
```

機微情報（社内の実ドメイン名、実メールアドレス等）が含まれる場合は抽象化して記録する。

## 9. テスト規約

### 8.1 テスト対象

| 対象 | テスト種別 | 優先度 |
|------|---------|--------|
| ユーティリティ関数（export/import/parse） | ユニットテスト | 必須 |
| カスタムフック（useMindMap, useHistory） | ユニットテスト | 必須 |
| コンポーネント | スナップショット or インタラクションテスト | 推奨 |
| E2E（ユーザー操作フロー） | Playwright | Phase 2 以降 |

### 8.2 テストファイル配置

テスト対象ファイルと同じディレクトリに置く。

```
src/utils/exportJSON.ts
src/utils/exportJSON.test.ts   ← 同階層
```

## 10. 依存ライブラリ管理

- `package.json` の `dependencies` / `devDependencies` を明確に分ける
- ライブラリ追加時は ADR または devlog に選定理由を記録する
- セキュリティアップデートは速やかに対応する（`npm audit` を定期実行）
- 不要なライブラリは都度削除する

---

## 11. 禁止事項

| # | 禁止 | 理由 |
|---|------|------|
| 1 | CSS カスタムプロパティ以外での色・サイズ指定 | DESIGN.md による再現性確保のため |
| 2 | `any` 型の無断使用 | 型安全性の維持 |
| 3 | `console.log` の本番コードへの混入 | ログの汚染防止 |
| 4 | `eval()` / `innerHTML` への文字列連結代入 | XSS 脆弱性防止 |
| 5 | `main` への直接コミット | 意図しないリリース防止 |
| 6 | 外部ライブラリの追加記録なし | 将来の依存関係管理のため |
