## 1. 総合評価

全体方針は妥当だが、現状のまま着工することは推奨しない。

特に以下は、ログイン不能、別ユーザーへのデータ紐付け、編集内容の消失につながるため、実装開始前に設計を修正する必要がある。

1. `SameSite=Strict` と OAuth コールバックの矛盾
2. heteml の公開ディレクトリ構成との不一致
3. メールアドレスを利用した自動アカウント統合
4. オートセーブ完了前の画面遷移と更新競合
5. ユーザー無効化・管理者降格後の既存セッション

一方、以下の方針は適切である。

- 機密情報や `vendor/` を Web 公開領域外に配置する
- フロントエンドと API を同一オリジンで提供する
- ログイン成功時にセッション ID を再生成する
- マップ・フォルダに所有者チェックを適用する
- Zip を非公開領域で生成し、即時削除と cron を併用する
- フォルダ削除時にマップを削除せずルートへ戻す

## 2. 実装開始前に修正すべき問題

### 2.1 【重大】`SameSite=Strict` では OAuth コールバック時にセッションを復元できない

#### 該当箇所

- `基本設計書_Phase2.md` 102～117行
- `基本設計書_Phase2.md` 143～149行

#### 問題

認証開始時にセッションへ `state` を保存しているが、Google または Microsoft からアプリへ戻る OAuth コールバックはクロスサイトのトップレベル遷移となる。

`SameSite=Strict` を設定したセッション Cookie はこのコールバックに送信されないため、サーバーは認証開始時のセッションを復元できず、保存済みの `state` を取得できない。

#### 想定される実害

- `state` 不一致としてログインが失敗する
- ログイン画面と SSO 画面を繰り返す状態になる
- ブラウザごとに挙動が異なり、原因調査が難しくなる

#### 推奨対応

- OAuth コールバックが GET である場合、認証トランザクションに使用する Cookieを `SameSite=Lax` とする
- セッション Cookie を次のように設定する
  - `Secure`
  - `HttpOnly`
  - `Path=/`
  - `SameSite=Lax`
  - 可能であれば `__Host-` 接頭辞
- `SameSite` のみに CSRF 対策を依存せず、変更系 API ではセッションに紐付いた CSRF トークンを検証する
- `state` に有効期限、一回限り使用、provider との紐付けを設ける

#### 参考資料

- [IETF Cookies: HTTP State Management Mechanism](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis/)

### 2.2 【重大】heteml の公開ディレクトリ構成と設計が一致していない

#### 該当箇所

- `基本設計書_Phase2.md` 31～49行

#### 問題

設計では `public_html/` を Web 公開領域としているが、heteml は `web/` 以下を公開領域として使用し、ドメインごとに公開フォルダを設定する。

一般的には次のような構成となる。

```text
/
├── mindmap-app/            # Web 非公開
└── web/
    └── example.com/        # 対象ドメインの公開フォルダ
        ├── index.html
        ├── assets/
        ├── api/
        │   └── index.php
        └── .htaccess
```

そのため、設計に記載された `../../mindmap-app/src` という相対パスも正しくない可能性が高い。

#### 想定される実害

- デプロイしてもサイトが表示されない
- PHP の `require` が失敗して API が全面的に動作しない
- パス調整時の誤りにより、機密ファイルを公開領域へ配置してしまう

#### 推奨対応

- heteml 管理画面で対象ドメインの実際の公開フォルダを確認する
- 構成図の `public_html/` を `web/<対象ドメイン>/` に修正する
- アプリ本体、`.env`、`vendor/`、一時ファイルを `web/` の外へ置く
- `realpath()` で解決したパスが期待する非公開ディレクトリであることを確認する
- デプロイスクリプトに、公開領域へ `.env` や `vendor/` が含まれていないことを確認する処理を追加する

#### 参考資料

- [heteml FTP・ディレクトリ構造](https://support.heteml.jp/hc/ja/articles/360042620293-FTP-%E3%81%AB%E3%81%A4%E3%81%84%E3%81%A6)

### 2.3 【重大】メールアドレスによる自動アカウント統合で他人のデータにアクセスできる可能性がある

#### 該当箇所

- `基本設計書_Phase2.md` 119～141行
- `基本設計書_Phase2.md` 316～335行

#### 問題

外部 Identity が未登録の場合に、同じメールアドレスの既存ユーザーを検索し、新しい Identity をそのユーザーへ自動追加する設計となっている。

メールアドレスは変更・再利用される可能性があるため、恒久的なユーザー識別子として安全ではない。

例えば、退職者が使用していたメールアドレスが新しい社員へ割り当てられた場合、新しい社員の SSO Identity が退職者の既存 `users.id` に追加され、退職者のマップへアクセスできる可能性がある。

#### 想定される実害

- 別ユーザーのマップ内容が漏えいする
- 旧利用者のデータを新利用者が更新・削除できる
- Google と Microsoft の別人アカウントが誤って統合される

#### 推奨対応

- Identity の一意キーを `issuer + subject` とする
- Microsoft は `tid + oid`、または検証済みの `iss + sub` で識別する
- メールアドレスは表示・連絡用属性として扱い、データ所有者の主キーにしない
- Google と Microsoft の統合は、既存アカウントへログイン中に両方を再認証する明示的な「アカウント連携」とする
- メールアドレスだけを根拠に既存アカウントへ Identity を自動追加しない
- Google Workspace の組織判定には、検証済みメールに加えて `hd` claim を利用する
- Microsoft の組織判定では、許可テナント ID とメンバー／ゲストの扱いを明確化する

#### 参考資料

- [Google OpenID Connect API Reference](https://developers.google.com/identity/openid-connect/reference)
- [Microsoft ID token claims reference](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference)

### 2.4 【重大】オートセーブ完了前の画面遷移で編集内容を失う

#### 該当箇所

- `基本設計書_Phase2.md` 167～175行
- `基本設計書_Phase2.md` 208～218行
- `mindmap-tool/src/hooks/useLocalStorage.ts` 29～41行

#### 問題

設計では、オートセーブ中であるため「一覧に戻る」際の保存待ちは不要としている。一方、保存処理には 500ms のデバウンスがある。

最後の編集から 500ms 以内に画面を離れた場合、保存リクエストがまだ送信されていない可能性がある。

現在の Phase 1 実装も、コンポーネントのアンマウント時にはタイマーをキャンセルするだけで、保留中の内容を保存していない。

また、複数の PUT リクエストが並行すると、古いリクエストが後から完了し、新しい内容を古い内容で上書きする可能性がある。

#### 想定される実害

- 「保存済み」と思って一覧へ戻ったユーザーの直近編集が消える
- 通信が遅い環境で過去の内容へ巻き戻る
- 複数タブで編集した場合に、一方の変更が無警告で消える

#### 推奨対応

- 画面遷移前にデバウンスを flush する
- 最新内容に対するサーバー応答を待ってから遷移する
- 保存待機中は「保存中」と表示し、遷移を保留する
- 保存リクエストを直列化する
- `revision` または ETag / `If-Match` による楽観ロックを導入する
- 保存対象の内容を先に IndexedDB へ保持してからサーバーへ送信する
- 「保存済み」は最新 revision のサーバー応答後にのみ表示する
- サーバー保存失敗時の再送・復旧フローを用意する

### 2.5 【高】ユーザー無効化と管理者降格が既存セッションへ即時反映されない

#### 該当箇所

- `基本設計書_Phase2.md` 109～149行
- `基本設計書_Phase2.md` 408～417行

#### 問題

ログイン時に `role` をセッションへ保存する設計だが、ユーザーの `status` を確認する処理が明記されていない。

また、管理者を一般ユーザーへ降格しても、既存セッションに保存された `role=admin` が残る可能性がある。

#### 想定される実害

- 無効化されたユーザーが再ログインできる
- 無効化後も既存セッションでマップへアクセスできる
- 降格された管理者が管理 API を継続利用できる

#### 推奨対応

- ログイン時に `users.status = 'active'` を必須条件として確認する
- 認証ミドルウェアで、現在の `status` と `role` を DB から確認する
- または `session_version` / `security_stamp` を導入し、無効化・降格時に既存セッションを失効させる
- 許可リスト削除時に既存セッションをどう扱うか決定する
- 権限変更と監査ログ記録を同一トランザクションで行う

### 2.6 【高】OIDC ID トークン検証が未確定・不足している

#### 該当箇所

- `基本設計書_Phase2.md` 100～117行
- `基本設計書_Phase2.md` 476～488行
- `基本設計書_Phase2.md` 556～565行

#### 問題

認証フローでは `state` 検証と UserInfo 取得のみが具体化され、ID トークンの検証内容が明確になっていない。

特に Microsoft の `common` エンドポイントでは、テナントごとに issuer が異なるため、単純な固定文字列比較では正しく検証できない。

#### 推奨対応

基本設計で次の検証項目を確定する。

- Discovery Document と JWKS を利用した署名検証
- 許可する署名アルゴリズムの固定
- `kid` による鍵選択と鍵ローテーションへの対応
- `iss` の検証
- `aud` / `azp` の検証
- `exp` / `iat` の検証
- `nonce` の照合
- Microsoft の `iss` と `tid` の整合確認
- UserInfo の `sub` と ID トークンの `sub` の一致
- PKCE S256
- `state` の一回限り使用、有効期限、provider との紐付け
- 認可コード、ID トークン、アクセストークンをログへ出力しない

#### 参考資料

- [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0-18.html)
- [Microsoft access token validation](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens)
- [OAuth 2.0 Security Best Current Practice](https://datatracker.ietf.org/doc/rfc9700/)

### 2.7 【高】異なる所有者のマップとフォルダを DB が関連付けられる

#### 該当箇所

- `基本設計書_Phase2.md` 351～370行
- `基本設計書_Phase2.md` 383～386行
- `基本設計書_Phase2.md` 401行

#### 問題

`mindmaps.user_id` と、`mindmaps.folder_id` が参照する `folders.user_id` の一致を保証する制約がない。

自分のマップに対して他人の `folder_id` を指定した場合、対象マップだけを `WHERE user_id = :current_user_id` で確認しても、移動先フォルダの所有者が検証されていなければ DB は更新を受け入れる。

#### 推奨対応

- 移動先フォルダについても同じユーザーの所有物であることを検査する
- 検査と更新を同一 SQL または同一トランザクション内で行う
- 可能であれば、次のような複合外部キーで DB レベルでも保証する

```sql
ALTER TABLE folders
  ADD UNIQUE KEY uq_folders_id_user (id, user_id);

ALTER TABLE mindmaps
  ADD CONSTRAINT fk_mindmap_folder_owner
  FOREIGN KEY (folder_id, user_id)
  REFERENCES folders (id, user_id);
```

- 所有していない ID へのアクセスは、存在確認による情報漏えいを避けるため原則 404 とする

### 2.8 【高】サーバー側バリデーション・容量制限・レート制限が不足している

#### 該当箇所

- `基本設計書_Phase2.md` 360～386行
- `基本設計書_Phase2.md` 388～417行
- `セキュリティポリシー.md` 29～35行
- `セキュリティポリシー.md` 63～89行

#### 問題

`mindmaps.data` を MySQL の JSON 型にしても、JSON としての構文しか検証されない。

ノード数、階層、テキスト長、ID 重複、テーマ値などは検証されず、クライアントを介さずに巨大・不正な JSON を送信できる。

また、セキュリティポリシーに記載されたレート制限が基本設計へ反映されていない。

#### 想定される実害

- DB・ディスク容量の枯渇
- Zip生成による CPU・一時領域の圧迫
- 他ユーザーを含むサービス全体の遅延・停止
- 不正データを開いた際のフロントエンド停止

#### 推奨対応

- HTTP リクエストサイズの上限を設定する
- Phase 1 と同等以上のスキーマ検証をサーバー側でも行う
  - データサイズ
  - スキーマバージョン
  - 必須フィールド
  - ノード数
  - 深さ 50
  - テキスト長 500
  - ID の形式と重複
  - テーマ値
- ユーザーごとのマップ件数・総容量・フォルダ数に上限を設定する
- Zip のマップ件数、合計容量、同時生成数に上限を設定する
- 認証、保存、ダウンロード、管理 API にレート制限を設ける
- 一覧 API、ユーザー一覧、監査ログにページネーションを設ける

### 2.9 【高】CSRF 対策の具体仕様がない

#### 該当箇所

- `基本設計書_Phase2.md` 388～417行
- `基本設計書_Phase2.md` 443～445行
- `セキュリティポリシー.md` 29～35行

#### 問題

`client.ts` に「CSRF 対策込み」と記載されているだけで、トークンの発行・保存・送信・検証方法が定義されていない。

OAuth の `state` は OAuth コールバックに対する CSRF 対策であり、マップ更新や管理 API の CSRF 対策にはならない。

#### 推奨対応

- セッションに紐付くランダムな CSRF トークンを発行する
- `POST`、`PUT`、`DELETE` の全 API で `X-CSRF-Token` ヘッダーを検証する
- `Origin` を検証し、必要に応じて `Referer` も補助的に確認する
- JSON API は `Content-Type: application/json` を必須にする
- ログイン成功時に CSRF トークンを更新する
- ログアウト API にも CSRF 対策を適用する

## 3. ユーザーへの実害につながる仕様の曖昧さ

### 3.1 保存先トグルがサーバーとの紐付け状態を兼ねている

#### 該当箇所

- `基本設計書_Phase2.md` 208～237行

#### 問題

既存のサーバーマップを「ローカルに保存」へ切り替えた場合、`mindmapId` を維持するのか破棄するのか定義されていない。

破棄する場合、再び「サーバーに保存」へ切り替えると新規マップとして POST され、重複が発生する。

#### 推奨対応

次の状態を分離する。

```text
binding:
  local
  server(id, revision)

autosaveTarget:
  local
  server
```

- サーバーマップの「ローカル保存」は、サーバー同期の一時停止として `mindmapId` を維持する
- サーバーとの紐付けを解除する場合は「ローカルコピーとして分岐」など別操作にする
- サーバーへ戻す際は revision を確認し、競合がある場合はユーザーに選択させる
- ローカル保存へ切り替えても既存のサーバーコピーは削除されないことを画面に表示する

---

### 3.2 ローカルフォールバックがユーザーごとに分離されていない

#### 該当箇所

- `基本設計書_Phase2.md` 210～216行
- `mindmap-tool/src/hooks/useLocalStorage.ts` 5～27行

#### 問題

現在の Phase 1 は `mindmap-data` という単一の localStorage キーを使用している。

共用端末でログアウト後に別ユーザーが利用した場合、前ユーザーのマップが読み込まれる可能性がある。

#### 推奨対応

- サーバーマップのフォールバックには IndexedDB を使用する
- `internal_user_id + mindmap_id` で保存領域を分離する
- 認証前にサーバーマップのフォールバックを自動表示しない
- 別ユーザーのデータを復元候補として表示しない
- 保存成功済みデータと未送信データを区別する
- ログアウト時は、未送信データがある場合にエクスポート・保持・削除を選択できるようにする
- 認証トークンは localStorage / IndexedDB に保存しない

---

### 3.3 マップ削除に確認・ゴミ箱・復元仕様がない

#### 該当箇所

- `基本設計書_Phase2.md` 282～283行
- `基本設計書_Phase2.md` 400行

#### 問題

要件定義書で明示されていないマップ削除機能が、API と画面メニューへ追加されている。一方で、削除前確認や復元方法が定義されていない。

#### 想定される実害

- メニューの誤操作による永久的なデータ消失
- タッチパッドやキーボード操作による意図しない削除
- サポート側で復旧できない

#### 推奨対応

- Phase 2 で必要でなければマップ削除をスコープから外す
- 実装する場合はソフトデリートとゴミ箱を採用する
- 復元可能期間を決める
- 削除前に対象名を明示した確認ダイアログを表示する
- 削除・復元・完全削除を監査ログへ記録する

---

### 3.4 最後の管理者保護に競合条件がある

#### 該当箇所

- `基本設計書_Phase2.md` 164～165行

#### 問題

複数の管理者が同時に別の管理者を降格・無効化すると、両方が「他に管理者がいる」という事前確認を通過し、最終的に管理者がゼロになる可能性がある。

#### 推奨対応

- 管理者数確認と更新を同一トランザクションで実施する
- 対象となる管理者行または管理用ロック行を `SELECT ... FOR UPDATE` でロックする
- 更新直前に有効な管理者数を再確認する
- 自分自身の降格禁止だけに依存しない

---

### 3.5 「日本国内の利用者のみを担保」という要件を満たせない

#### 該当箇所

- `基本設計書_Phase2.md` 540～552行
- `要件定義書.md` 282～288行

#### 問題

メールドメインまたはメールアドレスによる許可は、利用者の所属候補を制限するものであり、アクセス元が日本国内であることを保証しない。

許可されたユーザーは海外からも利用できる。

#### 推奨対応

- IP ジオブロックを行わない方針を維持する場合、要件名を「許可された組織・利用者の制限」へ変更する
- 「日本国内からのみアクセス可能」という表現を使用しない
- データ所在地とアクセス元地域を別要件として扱う
- 本当に国外アクセスを禁止する場合は、IdP の条件付きアクセスや IP 制限を別途導入する

#### 参考資料

## 4. 運用・構築面の追加修正

### 4.1 PHP バージョンを固定する

`PHP 8.x` では対象範囲が広すぎる。

2026年7月時点では PHP 8.2 のセキュリティサポートが2026年末までであり、構築時点での残存期間が短い。

heteml の対象サーバーで使用可能なバージョンを確認し、原則として PHP 8.4 など具体的なバージョンへ固定する。

参考資料:

- [PHP Supported Versions](https://www.php.net/supported-versions.php)
- [heteml PHP バージョン情報](https://support.heteml.jp/hc/ja/articles/360042135454-CGI-SSI-PHP-sendmail)

### 4.2 HTTP セキュリティヘッダーを設計する

`.htaccess` に少なくとも次を定義する。

- HTTP から HTTPS への強制リダイレクト
- `Strict-Transport-Security`
- 本番用 `Content-Security-Policy`
- `frame-ancestors 'none'`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy`
- 必要最小限の `Permissions-Policy`

本番 CSP では、現在の `script-src 'unsafe-inline'` を必要性確認のうえ除去する。

### 4.3 キャッシュ制御を設計する

次のレスポンスは `Cache-Control: no-store` を基本とする。

- `/api/auth/*`
- OAuth コールバック
- `/api/mindmaps/*`
- `/api/admin/*`
- JSON / Zip ダウンロード

静的アセットのみ、ファイル名ハッシュを前提に長期キャッシュする。

### 4.4 エラー・ログの取り扱いを設計する

- 本番では `display_errors=Off`
- エラー内容は一般化してクライアントへ返す
- 調査用の相関 ID を返す
- OAuth 認可コード、アクセストークン、ID トークンをログへ出さない
- マップ本文を通常ログ・監査ログへ出さない
- ログイン拒否ログへ不要な個人情報を保存しない

### 4.5 Zip生成の上限と異常終了時処理を追加する

- フォルダ内マップ数の上限
- 合計非圧縮サイズの上限
- ユーザーごとの同時実行数
- アプリ全体の同時実行数
- ユーザーごとの一時ディレクトリ
- ランダムで推測困難なファイル名
- `finally` と shutdown handler による削除
- cron が削除対象とするパス・ファイルパターンの限定

heteml では高負荷な cron が停止される可能性があるため、cron のみを正常系の削除手段にしない。

参考資料:

- [heteml cron 設定](https://support.heteml.jp/hc/ja/articles/360042620493-cron-%E8%A8%AD%E5%AE%9A)
- [heteml cron の制限](https://support.heteml.jp/hc/ja/articles/360041678754-cron-%E3%81%AF%E5%88%A9%E7%94%A8%E5%8F%AF%E8%83%BD%E3%81%A7%E3%81%99%E3%81%8B)

### 4.6 バックアップと復元を設計する

- Web ファイルと DB のバックアップ対象を確認する
- RPO、RTO、保存世代数を決める
- バックアップからの復元手順を文書化する
- 定期的に復元テストを行う
- アプリケーションの誤削除に備え、DB バックアップだけでなくソフトデリートも利用する

### 4.7 DB定義を補強する

DDLへ次を明記する。

- `ENGINE=InnoDB`
- `utf8mb4`
- 照合順序
- アプリ・DBで使用するタイムゾーンは UTC
- `mindmaps(user_id, folder_id, updated_at)` 等の検索用インデックス
- `audit_logs(created_at, id)` 等のページネーション用インデックス
- メール・ドメインの正規化規則
- 国際化ドメインを許可する場合の IDNA / Punycode 規則

### 4.8 監査ログの運用仕様を追加する

- 保存期間
- 閲覧権限
- ページネーション
- 検索・絞り込み
- 個人情報のマスキング
- OAuth トークンやマップ本文を保存しない規則
- 管理者自身による操作も必ず記録する
- ロール変更では変更前・変更後を記録する

## 5. データモデル・表示上の不整合

### 5.1 マップタイトルの正本が不明

DBには `mindmaps.title` があり、JSONには `root.text` がある。

ダッシュボードのファイル名、Zip内のファイル名、個別ダウンロード名にどちらを使うかを定義する必要がある。

推奨方針:

- マップタイトルは `mindmaps.title` を正本とする
- ルートノード名とは別に変更できるかを明確にする
- ファイル名に使用する場合は、制御文字やファイルシステム上の禁止文字を除去する
- 同名ファイルがZip内に存在する場合の連番規則を定義する

### 5.2 作成日時・更新日時が二重管理される

DBに `created_at` / `updated_at` があり、`MindMapFile` にも `createdAt` / `updatedAt` がある。

サーバーマップではDB日時を正本とし、ダウンロード時に `MindMapFile` へ反映する方針が安全である。

クライアントが送信した日時をDBの更新日時として信用してはならない。

### 5.3 ストレージ使用量の表示が実使用量とは一致しない

`SUM(LENGTH(data))` は論理的なデータサイズの目安であり、MySQL JSON のバイナリ表現、インデックス、行管理領域、バックアップ、一時ファイルを含む実ディスク使用量とは一致しない。

画面では「マップJSONの概算容量」と表示するか、実ストレージ量とは異なることを説明する。

## 7. 最低限必要な追加テスト

### 認証

- `state` 不一致、期限切れ、再利用を拒否する
- 不正署名、誤った `aud`、期限切れ ID トークンを拒否する
- Microsoft の `iss` と `tid` が一致しないトークンを拒否する
- Google の `hd` が許可ドメインと一致しない場合を拒否する
- 同じメールアドレスでも異なる主体を自動統合しない
- メールアドレス再利用時に旧ユーザーのデータへアクセスできない

### 認可

- 他ユーザーのマップを取得・更新・削除・ダウンロードできない
- 他ユーザーのフォルダへ自分のマップを移動できない
- 無効化されたユーザーの既存セッションが使用できない
- 降格された管理者の既存セッションで管理 API を利用できない
- 同時操作でも最後の管理者を無効化・降格できない

### 保存

- 最後の編集直後に一覧へ戻っても内容が保存される
- 通信順序が逆転しても古い内容で上書きされない
- 複数タブの競合を検知する
- サーバー保存失敗後にローカル内容を復旧できる
- 別ユーザーのローカルフォールバックが表示されない

### 容量・異常系

- 上限を超えるJSONを拒否する
- 階層、ノード数、テキスト長の上限を検証する
- 巨大フォルダのZip生成を拒否する
- ダウンロード中断後も一時ファイルが削除される
- cron が無関係なファイルを削除しない
