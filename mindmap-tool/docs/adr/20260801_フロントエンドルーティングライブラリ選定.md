# ADR: フロントエンドルーティングライブラリの選定

**日付**: 2026-08-01
**ステータス**: 承認
**関連**: 基本設計書_Phase2.md §7, §12 未決定事項 No.3、開発ステップ_Phase2.md Step 4

## 背景

Phase 1 のフロントエンドは「マインドマップ編集画面」1枚だけの SPA で、ルーティングを
持っていなかった。Phase 2 では以下の画面が追加される。

- ログイン画面（FR-07）
- ダッシュボード（FR-09）
- 管理コンソール（FR-08）
- ゴミ箱（FR-14）
- マインドマップ編集画面（既存）

さらに、サーバー側の認証フローがログイン成功時に `APP_URL/dashboard` へ、失敗時に
`APP_URL/login?error=...` へリダイレクトする実装（Step 3）になっており、**URLパスが
画面に対応している**ことが前提になっている。ハッシュベースの自前切り替えでは
このリダイレクト先を受け止められない。

基本設計書 §12 未決定事項 No.3 が「`react-router` 等の導入要否」として残っていた。

## 選択肢

### 1. 自前のルーター（`useState` で画面を切り替える）

- 利点: 依存が増えない。
- 欠点: URLと画面が対応しないため、サーバーからの `/dashboard` `/login?error=...`
  リダイレクトを受け止められない。ブラウザの戻る／進む、URLの直接入力、
  「一覧に戻る」からの遷移など、Phase 2 の要件で当然に期待される挙動をすべて
  自前で実装することになる。History API を自前で扱い始めた時点で、実質的に
  ルーターを書いているのと変わらない。

### 2. `react-router-dom`（採用）

- 利点: React のルーティングにおける事実上の標準。宣言的なルート定義、`Navigate` に
  よるリダイレクト、`useSearchParams` によるクエリ取得（`?error=` の読み取りに使う）が
  そろっており、認可ガード（`RequireAuth` / `RequireAdmin`）を素直に書ける。
- 欠点: 依存が1つ増える。ライブラリのバージョン間で API が変わってきた経緯がある。

### 3. `wouter` などの軽量ルーター

- 利点: バンドルサイズが小さい。
- 欠点: 今回必要なのは「複数画面 + 認可ガード + クエリ読み取り」という一般的な用途で、
  軽量さのために採用実績と情報量を犠牲にする理由が無い。バンドルサイズは、
  すでに reactflow / jspdf / html-to-image を含む本アプリでは支配的な要因にならない。

## 決定

**`react-router-dom` v7 を採用する。**

理由:

1. サーバー側の認証フローがパスベースのリダイレクト（`/dashboard`, `/login?error=...`）を
   前提に実装済みで、URLと画面の対応が必須要件になっている。
2. 認可ガードを「ルートをラップするコンポーネント」として表現でき、
   基本設計書 §3.2 の「一般ユーザーが `/admin` にアクセスした場合はダッシュボードへ
   リダイレクトする」をそのままコードにできる。
3. 軽量ルーターを選ぶ動機（バンドルサイズ）が、本アプリの構成では効かない。

## 影響

- `mindmap-tool/package.json` に `react-router-dom` を追加。
- `src/main.tsx` で `BrowserRouter` を導入し、`/login` `/dashboard` `/admin` `/editor` を定義。
  未知のパスは `/dashboard` へ寄せる。
- Phase 1 の編集画面（`App.tsx`）は `/editor` に配置し、ログイン必須とした。
- `vite.config.ts` の `base` を `/my-mindmap-tool/`（GitHub Pages 用）から `/` に変更した。
  Phase 2 は独自ドメインのルートに配置するため。
- **本番デプロイ時の注意**: `BrowserRouter` はパスベースのため、`/admin` などに直接
  アクセスされた場合に Apache が `index.html` を返すよう `.htaccess` の
  リライト設定が必要になる（Step 11 で対応する）。この対応が漏れると、
  ログイン後のリダイレクト先で 404 になる。

## 補足: ルート定義とサーバー側認可の関係

`RequireAdmin` はあくまで画面遷移の制御であり、権限の実体はサーバー側
（`AuthGuard::requireAdmin()`）にある。ガードを迂回して直接APIを叩いても 403 になるため、
フロントの実装ミスが権限昇格につながらない構造になっている。
